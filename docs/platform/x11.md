# X11 capture

X11 is the first supported session. A full-screen (or per-monitor) grab is possible without compositor cooperation, which is why Linux Miracast senders already work here.

## Approach

Preferred pipeline, matching GNOME Network Displays when the portal is missing:

1. Grab frames with GStreamer `ximagesrc` (or `XShm` / `XDamage` if a custom path is needed).
2. Convert / scale to the sink-negotiated size. The RTSP session parses `wfd_video_formats` from the sink, picks a progressive CEA/VESA/HH mode (prefer ≤30 fps, then the largest listed size), and the encoder scales to that width/height/fps.
3. Encode H.264.
4. Send RTP/UDP as part of the WFD session.

Audio is optional and off on the wire when the sink has no AAC, the user turns the switch off, or no Pulse/PipeWire monitor exists. When it is on, capture the default sink monitor (`pactl get-default-sink` + `.monitor`, or `PULSE_SOURCE`), encode AAC-LC stereo, and mux it with H.264 in MPEG-TS. GStreamer uses `pulsesrc provide-clock=true`; ffmpeg uses `aresample=async=1` so audio tracks the video clock. See [../constraints.md](../constraints.md).

## Why this works

On X11, any client that can talk to the X server can read the root window (subject to usual access controls). There is no Wayland-style “only the compositor may share pixels” rule. That is why GNOME Network Displays documents an X11 frame-grab fallback and why a DTK sender can ship on X11 before DDE ScreenCast exists.

## Requirements

- X11 session (`DGuiApplicationHelper::IsXWindowPlatform`)
- GStreamer plugins that provide `ximagesrc` (typically `gstreamer1.0-plugins-good`)
- Encoder elements (`x264enc` or a hardware encoder)
- Working Wi-Fi P2P / WFD stack (see [../constraints.md](../constraints.md))

## Limits

- Multi-monitor: stream one output, not the virtual union. `CastEngine` lists `QScreen` geometries; the encoder crops with `ximagesrc` `startx/starty/endx/endy` or `ffmpeg -video_size WxH -i :0+x,y`. Default is the primary screen.
- Cursor: `ximagesrc` can include the cursor; confirm the sink’s expected overlay.
- Performance: software encode is fine for slides; video/gaming needs hardware encode.
- Compositor effects (blur, scaling) are already in the framebuffer, so the sink sees what the user sees.

## What is not X11 support

Using this grab **inside a Wayland session** only captures XWayland windows. That path is invalid for “Wayland support.” See [wayland.md](wayland.md).
